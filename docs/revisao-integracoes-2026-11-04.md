Este relatório substitui a lista anterior de políticas locais. A documentação oficial determina os contratos; os testes determinam o que foi observado. As funcionalidades de consulta, relatórios, arquivos e seletores permanecem no projeto. README.md, AGENTS.md e SECURITY.md continuam excluídos na branch do PR #32.

## Sessão e limites operacionais

TELETHON_SESSION_DIR permite selecionar um diretório privado para reutilizar a sessão SQLite e o cache de entidades. O diretório é criado com modo 0700; os nomes de sessão derivam do token sem publicá-lo. Arquivos de sessão não são exportados nem entram no Git. Não configurar essa variável em um diretório compartilhado entre processos concorrentes.

Sem diretório configurado, o worker usa um diretório temporário privado e o remove ao desconectar. Há persistência SQLite e cache durante a execução; isso não cria persistência entre runners efêmeros do GitHub Actions. Não foi provisionado armazenamento durável de credenciais nem cache de sessão em artifacts/Actions cache.

O limite de cinco minutos da etapa de validação foi removido para não interromper uma espera legítima de rate limit. O timeout geral do job continua sendo um limite operacional do GitHub Actions, não um prazo definido pelo Telegram. O timeout de transporte HTTP também é uma decisão operacional, distinta das esperas retry_after/FLOOD_WAIT.

Erros sem resposta conclusiva não autorizam repetir uma escrita cegamente: a assinatura consultada de sendMessage não contém chave de idempotência. O cliente apresenta a falha; não afirma que a API garante entrega exatamente uma vez. Migração e rate limit com parâmetros oficiais têm tratamento explícito.

## Falhas explícitas e remoção de fallbacks automáticos

Esta revisão elimina o reenvio automático rico → HTML/texto no bot e no worker, a remoção de páginas já aceitas para tentar outro formato e o reenvio sem foto após a recusa da mídia. O formato do relatório é escolhido antes do envio pelo input formato (rich ou html; padrão rich), correspondente a FORMATO_MENSAGEM. HTML é um fluxo explícito e não depende da renderização rica. A atualização de status respeita a mesma escolha. Não se inicia um novo envio quando uma edição falha.

Foram removidos except/pass, o identificador opaco para participantes com construtor inesperado e a criação de entidades não confirmadas após duas recusas. Uma confirmação válida de getChat ainda pode ser utilizada; erros da tentativa adicional de username são registrados com código/descrição, e erros de autenticação são propagados. Hash zero e cache-miss continuam apenas nos casos documentados pelo protocolo.

Coletores capturam falhas esperadas de RPC, transporte ou Bot API e as registram com diagnóstico. TypeError, AttributeError e outras falhas de programação deixam de ser absorvidas como indisponibilidade. As fronteiras do processo registram tipo e localização (arquivo, função, linha), sem valores locais ou credenciais, e retornam falha. O validador real também preserva o diagnóstico oficial das APIs.

Falhas de download/envio da foto e erros de coleta no modo resumo agora impedem declarar conclusão integral, inclusive sem chat de destino. Recusas parciais geram aviso explícito e status não zero; não são reinterpretadas como dados, inexistência de peer ou sucesso. A notificação de erro é um fluxo de controle explícito, não o reenvio do relatório em outro formato. Uma edição inalterada é reconhecida sem segundo envio.

Fontes: [erros MTProto](https://core.telegram.org/api/errors), [envelope Bot API](https://core.telegram.org/bots/api#making-requests) e [RPC Errors Telethon](https://docs.telethon.dev/en/stable/concepts/errors.html).

Validação local desta rodada: recusa rica sem HTML alternativo e com status 1; HTML explícito sem renderizador rico; resumo parcial sem destino com status 1; erro de programação propagado com desconexão; duas recusas sem peer presumido; foto recusada sem segundo envio; erro inesperado HTTP propagado; diagnóstico sem valores sensíveis; status HTML inalterado sem novo envio e recusa de status propagada. Uma sondagem inicialmente estava sem BOT_TOKEN sintético e foi repetida com configuração corrigida. As seis sondagens JavaScript descritas acima, sintaxe, actionlint e compatibilidade Python 3.12/3.13 passaram. CI e consulta real do novo commit serão registradas na descrição do PR; as execuções anteriores não validam automaticamente estas mudanças.

A [CI desta rodada](https://github.com/morfalespi/IC/actions/runs/41930568330) e a [consulta real Bot API/MTProto](https://github.com/morfalespi/IC/actions/runs/41930595567), no commit c7b1644, passaram. getMe, getChat, autenticação Telethon e mesmo canal com perfil completo foram confirmados, sem erros MTProto registrados na consulta. ## Retomada: sucesso HTTP coerente e autenticação fatal

A nova revisão confrontou [Making requests](https://core.telegram.org/bots/api#making-requests), [erros MTProto](https://core.telegram.org/api/errors) e [RPC Errors Telethon](https://docs.telethon.dev/en/stable/concepts/errors.html). Foram corrigidas quatro lacunas residuais:

- Um envelope ok=true não pode confirmar sucesso quando acompanhado por status HTTP de erro. A contradição é identificada como falha de protocolo, sem repetição automática.
- A recusa de autenticação Bot API, indicada por HTTP 401 ou pelo erro 401 do envelope, gera erro fatal distinto das recusas de uma leitura opcional. A recusa de autenticação MTProto também atravessa os coletores, em vez de ser agregada como erro opcional e seguida por novas leituras.
- Uma resposta getFull sem o perfil completo esperado é uma falha de protocolo; não é interpretada como perfil vazio obtido com sucesso.
- A notificação registra por que não foi solicitada, por que já estava confirmada ou por que não pôde ser enviada. Token ausente retorna status 1. Uma marca operacional, sem credenciais, impede nova tentativa de notificação com a autenticação Bot API já recusada na mesma execução. Falha ao gravar essa marca é registrada e não absorve a recusa original.

Essas decisões distinguem erro de protocolo, autenticação fatal, recusa de método e erro local. A marca de autenticação é controle do job no diretório RUNNER_TEMP, não uma resposta inventada da API nem prova de notificação entregue. As fronteiras de coleta preservam os erros 401; continuam sendo registrados os erros esperados de leituras opcionais que não invalidam a autenticação.

Sondagens locais passaram para HTTP 500/ok=true, corpo não JSON, erro 401 no HTTP ou envelope, bloqueio de notificação após recusa de autenticação, token ausente, perfil completo ausente, interrupção após AuthKeyUnregisteredError e desconexão do cliente. Sintaxe, actionlint e compatibilidade Telethon em Python 3.12/3.13 passaram. A CI e a leitura real do novo commit serão verificadas separadamente e vinculadas na descrição do PR.

## Correções após a revisão das ressalvas

A pesquisa em [Message](https://core.telegram.org/bots/api#message), [access_hash](https://core.telegram.org/api/peers#access-hash), [sessões Telethon](https://docs.telethon.dev/en/stable/concepts/sessions.html), [máscaras de logs](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#masking-a-value-in-a-log) e [condições de etapas](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsif) sustentou as seguintes mudanças:

- Notificação aceita com message_id=0 grava apenas notificacao_pendente. Não grava notificado e não é reenviada automaticamente. O estado confirmado exige resposta Message com identificador, data, tipo/ID de chat válidos e destino correspondente ao solicitado, considerando somente migração informada pela API. Isso confirma a resposta do servidor, não leitura humana pelo destinatário.
- Worker e notificador usam a mesma interpretação e gravação de estado. Recusa, pendência e confirmação não são intercambiáveis. O caminho de ficha definitiva também deixa de marcar uma mensagem pendente como confirmada.
- A exportação aplica redação recursiva antes de gerar JSONL, páginas completas e arquivos Markdown. access_hash, auth_key e outros campos explícitos de autenticação tornam-se [redigido]; valores conhecidos de credenciais e padrões de token são removidos dos textos. O objeto original e o cache usados nas chamadas das APIs não são alterados. O JSONL passa a declarar formato infocard-telegram-jsonl-v3 e a política de redação. Isso pode exigir adaptação de consumidores externos que validem estritamente a versão v2.
- A redação de credenciais não apaga os dados de perfil que constituem a funcionalidade do projeto. Identificadores, nomes e outros dados pessoais legitimamente retornados podem permanecer no relatório entregue ao chat autorizado. Não se trata de um mecanismo universal de anonimização.
- O workflow registra máscaras de alvo e IDs lendo GITHUB_EVENT_PATH antes de disponibilizá-los como variáveis às etapas. Os dados deixam de estar no env geral do job. O modo de consulta é uma escolha explícita completo/resumo; a rota validar_entrega é um teste de envio separado e opt-in. A máscara protege logs; o repositório e o transporte workflow_dispatch continuam públicos e não são declarados confidenciais.
- migrate_mode=dry-run não executa dispatch de healthcheck, injeção de credencial, publicação nem consulta posterior de webhook. Executa leitura de estado e prévia da migração. Valor de modo desconhecido falha explicitamente. Não foi executado deploy real para testar essa mudança. O gatilho automático em push para main continua existente; merge que altere os caminhos configurados ainda pode disparar publicação/migração safe.

As sondagens locais passaram para transição pendente/confirmada, supressão de reenvio pendente, Message inválida ou destino divergente, redação aninhada e em JSONL, preservação do objeto Telethon original, escape das máscaras e dry-run simulado com CLI substituída. Sintaxe, actionlint, diff --check e compatibilidade Python 3.12/3.13 passaram. O validador real agora confronta também a redação na exportação das respostas recebidas das APIs, sem imprimir valores sensíveis. CI e execução real do commit serão vinculadas no PR.

A validação real de envio depende de um chat de teste explicitamente autorizado. Nenhum destinatário é inferido de logs, perfil GitHub ou execuções anteriores. Foi solicitada essa informação separadamente; nenhum envio de teste foi executado sem ela.

A rota modo=validar_entrega está preparada para executar, sob escolha explícita do operador, uma mensagem e três documentos pequenos sintéticos (Markdown, JSONL e ZIP). Ela reutiliza os geradores e remetentes do projeto, exige Message correspondente ao chat, baixa cada documento por getFile e compara SHA-256. Pendência, ausência de Document ou divergência de bytes interrompem o teste com falha e sem reenvio. Modo/destino ausentes bloqueiam a rota antes de qualquer chamada. Não pode ser combinada com validar_apis e não aciona notificação extra de erro.

A integração dessa rota foi verificada com API simulada: os três documentos atravessaram os remetentes multipart e o downloader reais do projeto com bytes idênticos; corrupção de download falhou após o primeiro documento; Message pendente parou antes dos uploads; modo não explícito bloqueou todas as chamadas. Esta evidência não substitui autorização nem execução real no chat escolhido. Os logs de aceitação dos documentos foram corrigidos para não anunciar confirmação prematura.
